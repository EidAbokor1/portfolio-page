02 / Data & cost engineering#

S3 attribution & storage optimisation

S3 InventoryAthenaLambdaS3 Batch Operations
Technical details & approach+

01 / Project attribution

The problem

Large S3 datasets lacked consistent project attribution, making ownership and storage-cost allocation difficult.

What I did
  • Investigated metadata and existing mappings, then designed a workflow using S3 Inventory, Athena, S3 Batch Operations, Lambda, and object tagging.
  • Built a resolver that allocates objects only when there is enough evidence; uncertain objects remain unallocated.
  • Used version-aware manifests, dry runs, backups, and reconciliation, while preserving unrelated object tags.
Result

One dataset of roughly 803 TiB reached approximately 99% project allocation.

The takeaway

At this scale, explicit uncertainty and reversible changes matter as much as coverage.

02 / Noncurrent versions & cost analysis

The problem

Historical, noncurrent S3 object versions were consuming significant storage.

What I did
  • Used S3 Inventory and Athena to identify old versions and quantify potential storage savings.
  • Identified approximately 1.56 million noncurrent versions consuming around 210 TiB.
  • Helped establish tracking for archive and deletion savings and further lifecycle optimisation.
Estimated cost avoidance

Identified an estimated $60k in annualised storage-cost avoidance, with additional opportunities for lifecycle and archive optimisation. Realised savings require separate tracking.

The takeaway

Separate identified opportunities, estimates, and achieved savings when reporting cost impact.

03 / Concurrency & reliable processing

The problem

Increasing concurrency during large-scale S3 tagging correlated with more processing failures.

What I did
  • Tested different concurrency levels and compared reliability.
  • Explored whether ECS workers could provide more control over worker count, request rate, retries, and back-pressure.
  • Recognised that both Lambda and ECS still call S3 APIs; a runtime change alone would not remove downstream pressure.
Tested finding

Testing showed that reducing Lambda concurrency improved reliability. ECS workers remained an option under discussion for finer processing control.

The takeaway

The useful question is how fast millions of objects can be processed safely without overwhelming downstream systems.

The problem

Security alerts required manual investigation to locate affected code, identify an owner, and define remediation work.

What I did

  • Built a workflow that reads the finding and identifies the affected repository or dependency.
  • Used Git history to investigate likely ownership and checked Notion for duplicate tickets.
  • Prepared a consistent Service Desk ticket with evidence and remediation instructions, requiring human approval before writing.

Workflow built

Security findings become assigned, trackable remediation work with human control and an audit trail. After approval, the workflow creates one Notion ticket and does not modify Wiz or GitLab.

The takeaway

Useful automation can prepare the investigation while keeping consequential actions explicit and reviewable.
